# Brainstorm: schedule-calendar

> 来源：与用户口头澄清（2026-08-11），结论已收敛。  
> 注：对话中完成 brainstorm；本文件为决策落档。

## 1. 动机

工作流已有 `schedule`（cron）与后台轮询，但只能在列表/编辑页看到「每天 09:00」一类文案，**无法按日期纵览**。用户需要独立的「定时任务」能力，并以**日历**为主界面：哪一天有哪些任务、可新建/拖改。

## 2. 范围

### In
- 独立数据模型「定时任务」（`taskId` 区分实例）
- 侧栏**独立导航**（建议标签：**日历**）
- 月历 UI：**点空新建、点任务编辑、拖改时间**（C2）
- 动作类型（B3）：
  - `run_workflow`：触发已有工作流
  - `remind`：纯提醒（到点 UI/通知可见）
  - `run_skill`：绑定技能/脚本（本期接接口 + 最小可执行或明确 stub 行为）
- 与工作流定时 **R2 并存**：两边都可触发；若检测到同一工作流既有 `schedule.enabled` 又有日历任务会跑它 → **提示用户**，不自动关闭任一侧；用户自行管理
- 调度执行：到点按任务配置触发；运行记录可引用 `taskId`
- 持久化落在 `~/.shy`（sqlite 或等价）

### Out
- 云同步、多人协作日历
- 强制互斥（自动禁用工作流定时）
- 完整 Google Calendar 级 RRULE 编辑器（可用简化频率模型 + cron，与现有 WorkflowSchedule 对齐或扩展）
- 系统级 OS 通知权限的深度平台差异（可用应用内通知/状态条先行）

## 3. 主要决策（已决）

| # | 决策 | 选定 |
|---|------|------|
| D1 | 数据形态 | 独立定时任务实体，非仅工作流视图 |
| D2 | 导航 | 独立侧栏入口「日历」 |
| D3 | 动作 | B3：workflow + remind + skill（skill 接口先行/最小跑） |
| D4 | 与 workflow.schedule | R2 并存；重复只提示，用 taskId 区分 |
| D5 | 日历交互 | C2：月历 + 点空新建 + 拖改时间 |
| D6 | 防重复策略 | 不自动去重；提示 + 用户自管 |

## 5. 验收标准

1. 侧栏有「日历」；月视图展示当月各日任务实例（含重复展开）。
2. 点空白可新建；点任务可编辑/删除/启用停用；拖动能改时间并持久化。
3. 任务可配置三种动作；到点：提醒可见、工作流进入现有 run、技能按本期实现触发或明确 stub 日志。
4. 若工作流自身定时与日历任务同时会跑同一工作流，保存或日历加载时给出提示；两者仍可并存，实例以 taskId（及工作流 run）区分。
5. `npm run typecheck && npm test` 通过；关键调度/展开逻辑有单测。

## 6. 风险与权衡

- [Risk] R2 导致双跑 → Mitigation: 明确提示文案；运行记录带 taskId / trigger=calendar_task|workflow_schedule。
- [Risk] 拖拽改时间与「每周」重复规则冲突 → Mitigation: 拖拽默认改「下次发生」或「该系列的 time 字段」；设计里定一种并写进 UI 说明。
- [Trade-off] skill 本期若仅 stub → 接受，接口与 UI 先齐，执行可最小化为写日志 + 可选 invoke。
